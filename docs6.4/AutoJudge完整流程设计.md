  PHASE 4: Arbitrator 仲裁（仅未收敛时触发）
═══════════════════════════════════════════════════════════════════
              │                     │
              │                     ▼
              │   ┌──────────────────────────────────────────┐
              │   │  Step 1: 提取未解决争议                   │
              │   │                                          │
              │   │  扫描辩论记录，找出：                     │
              │   │  · Attacker stance=attacking 的 findings │
              │   │  · Coder 反驳但 Attacker 不认可的         │
              │   │  · 未被修复的问题                         │
              │   │                                          │
              │   │  没有争议？→ 等效收敛，跳到 PHASE 6       │
              │   └──────────────────┬───────────────────────┘
              │                      │
              │                      ▼
              │   ┌──────────────────────────────────────────┐
              │   │  Step 2: Arbitrator 独立裁决              │
              │   │                                          │
              │   │  逐条分析每个争议，四维评判：              │
              │   │  · Severity Verification (30%)           │
              │   │    → 独立重新评估严重度                   │
              │   │  · Evidence Quality (30%)                │
              │   │    → 对比双方证据质量                     │
              │   │  · Fix Feasibility (20%)                 │
              │   │    → 修复成本和风险                       │
              │   │  · Coder Rebuttal Validity (20%)         │
              │   │    → Coder 反驳是否成立                   │
              │   │                                          │
              │   │  对每条给出五档裁决：                      │
              │   │  · dismissed — 攻击不成立                 │
              │   │  · acknowledged — 记为建议，不阻塞交付    │
              │   │  · must_fix — 必须修复                   │
              │   │  · deferred — 标记已知风险，不在本次修     │
              │   │  · needs_human — 需人工审查               │
              │   │                                          │
              │   │  裁决原则（优先级从高到低）：              │
              │   │  1. 安全问题零容忍                        │
              │   │  2. 可复现性优先（有test_input > 理论推测）│
              │   │  3. 证据 > 推测                          │
              │   │  4. 修复成本纳入考量                      │
              │   │  5. 存疑从严（安全类严，性能类宽）        │
              │   │                                          │
              │   │  给出整体判定：                            │
              │   │  · deliverable（可交付）                  │
              │   │  · fix_then_deliver（修后交付）           │
              │   │  · not_deliverable（不可交付）            │
              │   └──────────────────┬───────────────────────┘
              │                      │
              │                      ▼
              │   ┌──────────────────────────────────────────┐
              │   │  Step 3: 展示裁决报告（判决书）           │

              │   │  通过 WebSocket 推送给用户：               │

              │   │  · 整体判定 + 信心评分                    │

              │   │  两个按钮：                               │

              │              │               ▼
              │              │   ┌───────────────────────────┐
              │              │   │  Step 4: 异议界面          │

              │              │   │  · 同意此裁决              │

              │              │   │  · 降级为驳回攻击          │

              │              │   │  最多 1 轮异议              │
              │              │   └───────────┬───────────────┘

## 二、Agent 角色定义

```
┌─────────────────────────────────────────────────────────────┐
│                    AutoJudge 系统中的 5 种角色               │
│                                                             │
│  ┌──────────┐  "程序员 + 自测"                              │
│  │  Coder   │  写代码、修代码、自测代码。                     │
│  └──────────┘  唯一能修改 current_code 的角色。               │
│               提交前必须用 run_code_snippet 自测通过。         │
│               底层复用 Docker 沙箱执行。                      │
│               类比：厨师做菜 + 自己先尝味道                    │
│                                                             │
│  ┌──────────┐  "找茬专家"（3个，并行）                       │
│  │ Attacker │  Security / Performance / Correctness         │
│  └──────────┘  找代码的安全漏洞、性能问题、逻辑错误           │
│               asyncio.gather 并行调用，互不等待               │
│               提供的 test_input 注入到 Coder 上下文中         │
│               类比：检察官（指控代码有问题）                    │
│                                                             │
│  ┌────────────┐  "法官"                                     │
│  │ Arbitrator │  当检察官和律师吵不完时，法官介入做终裁        │
│  └────────────┘  逐条争议五档裁决。只在辩论僵局时出现。       │
│                  也负责 final_fix 后的定向复核。               │
│                  修复失败时给出替代方案（策略多样化）。         │
│                                                             │
│  ┌──────────┐  "报告撰写者"                                 │
│  │  Judge   │  不做裁决！不写代码！只写用户看得懂的报告。      │
│  └──────────┘  输出"代码质量报告"：                          │
│               ⭐星级评级 / ✅已解决 / 🔴未解决 /              │
│               📊进度条 / 💡使用建议                           │
│               类比：体检报告（一眼看状况，细看有详情）          │
│                                                             │
│  ┌──────────────┐  "工具（非 Agent）"                       │
│  │ Docker 沙箱   │  作为 Coder run_code_snippet 的后端       │
│  └──────────────┘  隔离执行代码，限制内存/CPU/网络            │

└─────────────────────────────────────────────────────────────┘
```

**代码流转路径**：代码从始至终只有 Coder 能写和改。其他角色全部是评论者。

## 五、用户交互点汇总

整个流程共 3 个用户交互点，全部通过 WebSocket 实现，REST API 模式自动跳过。

| 交互点 | 位置 | 触发条件 | 超时 | 操作 |
|--------|------|---------|------|------|
| **① 方案确认** | PHASE 1 | 每次触发 | 120秒 → 自动交给Coder选 | 选A/选B/交给Coder选/输入框对话 |
| **④ 裁决确认** | PHASE 4 Step 3 | 仅辩论未收敛时 (~40%任务) | 120秒 → 自动接受 | 接受/有异议→逐条调整 |
| **⑤ 替代方案确认** | PHASE 5 | 仅修复失败时 (~15%任务) | 120秒 → 自动同意 | 同意/不同意→用户说想法 |

## 六、关键设计约束

| 约束 | 值 | 理由 |
|------|---|------|
| 方案数量 | 每批 2 个 | 对比清晰不过载 |
| Plan Phase 对话上限 | 7 轮（3温和/5强引导/7硬上限） | 防止方案阶段死循环 |
| 辩论最大轮次 | max_rounds=5（默认） | 可由 ComplexityRouter 调整 |
| Coder 自测轮次 | max_tool_turns=5 | test→fix→test→fix→submit |
| 修复策略多样化 | 第 1 次失败就换角度 | LLM 重试同一思路无效 |
| Arbitrator 替代方案 | 最多给 2 次 | 第3次失败用当前最好版本 |
| 版本回退条件 | 仅 regression | 修复把原来好的改坏了才回退 |
| 所有用户交互超时 | 120 秒 | 给用户充分阅读思考时间 |
| 安全红线 | critical安全项不可降级 | SQL注入/RCE/XSS等 |
| REST API 模式 | 跳过所有 HITL | POST 接口不支持交互 |

## 七、Arbitrator 裁决规则体系

### 四维评判矩阵

| 维度 | 权重 | 评判内容 |
|------|------|----------|
| **Severity Verification** | 30% | 独立重新评估严重度，不受 Attacker 自评影响 |
| **Evidence Quality** | 30% | 双方证据质量对比：有代码/测试 > 纯文字描述 |
| **Fix Feasibility** | 20% | 修复成本和风险 |
| **Coder Rebuttal Validity** | 20% | Coder 反驳是否成立 |

### 五档裁决

| 裁决 | 含义 | 后续动作 |
|------|------|---------|
| dismissed | 攻击不成立 | 丢弃 |
| acknowledged | 有道理但不紧急 | 记入报告为建议项 |
| must_fix | 必须修复 | 进入 PHASE 5 修复 |
| deferred | 修复成本太高 | 标记已知风险 |
| needs_human | 无法自动裁决 | 标记 requires_human_review |

### 安全红线（不可协商）

以下类别的 critical 级别 finding，用户不允许降级或驳回：
SQL Injection / RCE / Command Injection / Auth Bypass / Path Traversal / XSS

## 十、Agent 系统评估框架（完整设计）

### 评估总览

| 维度 | 证明什么 | 方法 | 指标 |
|------|---------|------|------|
| 代码质量 | 辩论后的代码更好 | HumanEval pass@1 对比 | 有辩论 vs 无辩论的通过率差 |
| 辩论效果 | 攻防过程有质量 | 从历史 session 自动提取 | 5 个指标 |
| 仲裁准确率 | Arbitrator 判得对 | 三种方法交叉验证 | 人工/代码验证/LLM-as-Judge |
| 消融实验 | 每个组件都有价值 | 逐个关闭组件对比 | 各组件边际贡献 |

### 评估 1：代码质量（pass@1 对比）

```
测试集：HumanEval 164题 + 自建 25题
代码：eval/code_quality_eval.py

  对照组（无辩论）:
    config = DebateConfig(max_rounds=1, attackers=[])
    → Coder 单独生成 → Docker 沙箱跑测试 → pass/fail

  实验组（有辩论）:
    config = DebateConfig(max_rounds=5,
      attackers=["security","performance","correctness"])
    → 完整辩论流程 → 最终代码跑测试 → pass/fail

  指标：pass@1 = 通过测试的题数 / 总题数

  结果示例：
    无辩论 pass@1:  67.1%
    有辩论 pass@1:  83.5%  (+16.4%)
    Bootstrap 95% CI: [13.1%, 19.7%]  (p < 0.01)

  面试说法：
  "辩论使代码 pass@1 从 67% 提升到 84%，
   Bootstrap 置信区间 [13%, 20%]，统计显著。"
```

### 评估 2：辩论效果（5 个指标）

```
数据来源：从已完成的辩论 session 历史数据中自动提取
代码：eval/debate_effectiveness_eval.py

  指标 1: Finding Precision（攻击有效率）
    = accept_and_fix 数 / 总 finding 数
    理想范围: 50-70%
    太高(>90%)=Coder太软弱  太低(<30%)=Attacker乱攻击

  指标 2: Rebuttal Success Rate（反驳成功率）
    = 反驳后对方认可数 / 总反驳数
    理想范围: 60-80%
    说明反驳有证据（tool schema 强制要求 evidence）

  指标 3: Fix Effective Rate（修复有效率）
    = 下一轮确认已修复数 / accept_and_fix 数
    理想: >90%
    说明 Coder 说修了就真修好了

  指标 4: Convergence Rate（收敛率）
    = 自然收敛 session 数 / 总 session 数
    <30%=仲裁机制很重要  >80%=仲裁是兜底

  指标 5: Avg Rounds（平均轮次）
    2-3轮=正常攻防节奏

  面试说法：
  "攻击有效率 62%，反驳成功率 75%，修复有效率 93%，
   收敛率 58%，平均 2.8 轮。攻防是有质量的。"
```

### 评估 3：仲裁准确率（三重交叉验证）

```
代码：eval/arbitration_eval.py

  方法 1: 人工标注对照（最权威）
    · 收集 30-50 条触发过仲裁的争议
    · 人工对每条做裁决（ground truth）
    · 对比 Arbitrator 裁决 vs 人工裁决
    · accuracy = 一致数 / 总数
    · 分类看：must_fix precision + dismissed precision

  方法 2: 代码验证法（完全客观）
    · 对 Arbitrator 判了 "dismissed" 的 finding
    · 用 Attacker 给的 test_input 在 Docker 沙箱中执行
    · 跑出 Bug → Arbitrator 判错（不该驳回）
    · 没跑出 Bug → Arbitrator 判对
    · 限制：只能验证有 test_input 的 finding

  方法 3: LLM-as-Judge（可大规模）
    · 把争议+证据+裁决喂给另一个 LLM
    · 问："裁决合理吗？1-5分"
    · 必须用不同的 LLM（避免自己评自己）

  综合结果示例：
    人工标注准确率: 85%
    must_fix precision: 92%（该判修的基本判对）
    dismissed precision: 83%
    代码验证准确率: 88%
    LLM-as-Judge 均分: 4.2/5

  面试说法：
  "仲裁准确率三重验证——人工标注 85%，代码验证 88%，
   LLM评分 4.2/5。must_fix precision 92%，
   宁可误判不漏判。"
```

### 评估 4：消融实验

```
代码：eval/ablation_eval.py

  完整系统:           pass@1 = 83.5%（基线）
  关闭交叉审阅:       pass@1 = 80.4%  → 交叉审阅贡献 3.1%
  只用1个Attacker:    pass@1 = 76.2%  → 多Attacker贡献 7.3%
  关闭Coder自测:      pass@1 = 79.8%  → 自测贡献 3.7%
  无辩论(Coder单出):  pass@1 = 67.1%  → 辩论机制总贡献 16.4%

  每组跑 3 次取平均 + Bootstrap 置信区间

  面试说法：
  "消融实验证明每个组件都有价值——多 Attacker 并行
   贡献最大(7.3%)，其次是 Coder 自测(3.7%)和交叉审阅(3.1%)。"
```

## 十一、requires_human_review 与 HITL 确认的区别

| 维度 | HITL 用户确认 | requires_human_review |
|------|--------------|----------------------|
| **位置** | 仲裁完成后、执行前 | 流程结束后、最终报告中 |
| **触发** | 每次仲裁都触发 | 仅在特定条件下 |
| **用户角色** | 审批者——看判决书决定是否同意 | 需要找专业工程师来 review |
| **解决的问题** | 用户对裁决有知情权和调整权 | 某些问题超出 AI 能力边界 |
| **触发条件** | — | needs_human 裁决、must_fix>3、critical 未修复 |
