## 一-B、方案设计环节详情（Plan Phase，最终版）

### 为什么需要

```
之前：需求 → Coder直接写（可能方向错）→ 3轮辩论 → 发现方向错 → 白费
现在：需求 → Coder出2个方案对比 → 用户选择/对话调整 → 写代码 → 辩论
      成本：5-10秒选择  节省：3-5分钟的方向性浪费
```

### 核心设计：2 个方案 + 对话式交互（v2 最终版）

```
┌─────────────────────────────────────────────────────────┐
│                    方案设计                               │
│                                                         │
│  需求：写一个用户登录接口                                │
│  我为你准备了 2 个方案，各有侧重：                       │
│                                                         │
│  ┌─ 方案 A：轻量级 ─────────────────────────────────┐   │
│  │  技术：FastAPI + bcrypt + JWT                     │   │
│  │  特点：简洁，依赖少，适合 MVP 或小型项目           │   │
│  │  核心流程：                                       │   │
│  │    接收用户名密码 → bcrypt 校验 → 签发 JWT        │   │
│  │  安全：bcrypt cost=12，JWT 30分钟过期             │   │
│  │  不含：刷新 token、多因素认证                      │   │
│  │  [选择方案 A]                                     │   │
│  └──────────────────────────────────────────────────┘   │
│                                                         │
│  ┌─ 方案 B：生产级 ─────────────────────────────────┐   │
│  │  技术：FastAPI + bcrypt + JWT + Redis             │   │
│  │  特点：完整，含 token 刷新和会话管理               │   │
│  │  核心流程：                                       │   │
│  │    接收凭证 → bcrypt 校验 → 签发 access+refresh   │   │
│  │    token → Redis 存储 session                     │   │
│  │  安全：bcrypt + 双 token + Redis 黑名单           │   │
│  │  不含：多因素认证、OAuth 第三方登录                │   │
│  │  [选择方案 B]                                     │   │
│  └──────────────────────────────────────────────────┘   │
│                                                         │
│  [交给 Coder 选择最佳方案]                               │
│                                                         │
│  ┌─────────────────────────────────────────────────┐   │
│  │  💬 有想法？直接告诉我：                          │   │
│  │  ┌─────────────────────────────────────────┐    │   │
│  │  │  (输入框：输入你的需求补充或方案调整...)   │    │   │
│  │  └─────────────────────────────────────────┘    │   │
│  │                                    [发送]       │   │
│  └─────────────────────────────────────────────────┘   │
│                                                         │
│  (超时 120 秒自动交给 Coder 选择最佳方案)                 │
└─────────────────────────────────────────────────────────┘
```

### 3 种用户操作

| 操作 | 用户做什么 | 系统反应 |
|------|-----------|---------|
| **选择方案 A/B** | 点按钮 | Coder 按该方案写代码 |
| **交给 Coder 选择最佳方案** | 点按钮 | Coder 综合分析后自主择优，**说明选择理由**后写代码 |
| **输入框打字** | 自然语言对话 | Coder 基于输入调整方案，实时更新卡片 |

> 去掉了「换一批」按钮——输入框已完全覆盖此功能。
> 「交给 Coder 选」时不需要 Attacker 参与——Attacker 在辩论阶段会全面审查，方案阶段重复参与增加延迟不增加质量。

### 输入框支持多轮对话

```
用户："我不想用 Redis，服务器没装。"
Coder：（更新方案卡片，Redis 方案改为 SQLite 或纯 JWT）

用户："并发大概 50 左右，够用吗？"
Coder："50 并发 SQLite 完全够用。方案 A 适合你的场景。"

用户："好，就 A 吧"  →  等效于点击 [选择方案 A]
```

### 防死循环：三层防护

用户和 Coder 可能在方案阶段无限协商（"要Redis→不要→还是要→又不要..."）。

```
  轮次 1-2：自由讨论（正常）

  轮次 3：温和提示
  ┌─────────────────────────────────────────────┐
  │ 💡 已调整 3 轮。建议先选一个开始——             │
  │ 后续辩论阶段还可以继续优化。                   │
  └─────────────────────────────────────────────┘

  轮次 5：强引导 + 矛盾检测
  ┌─────────────────────────────────────────────┐
  │ ⚠️ 我注意到你对 Redis 的偏好有反复：            │
  │  · 第1轮：要用 Redis                          │
  │  · 第3轮：不要 Redis                          │
  │  · 第5轮：还是要 Redis                        │
  │                                              │
  │ 核心纠结似乎是：想要缓存能力，但担心部署复杂。  │
  │ 折中方案：先用内存缓存，代码预留 Redis 接口。    │
  │                                              │
  │ [选择折中方案]  [选方案A]  [选方案B]            │
  └─────────────────────────────────────────────┘

  轮次 7（硬上限）：自动推进
  ┌─────────────────────────────────────────────┐
  │ 综合你前面的反馈，Coder 选择最佳方案开始写。   │
  │ 如果后续需要调整方向，辩论阶段仍可修改。       │
  └─────────────────────────────────────────────┘
  → 自动执行 [交给 Coder 选择最佳方案]

  任何轮次 120 秒无响应 → 自动推进
```

### 流程图

```
  用户提交需求
         │
         ▼
  Coder 生成 2 个方案（不同技术路线）
         │
         ▼ WebSocket 推送
  ┌──────────────────────────────────────────┐
  │  方案卡片 A + 方案卡片 B                  │
  │  [选A]  [选B]  [交给Coder选最佳方案]       │
  │  💬 输入框                                │
  └────────────────────┬─────────────────────┘
                       │
       ┌───────────────┼───────────────┐
       │               │               │
    点选方案    交给Coder选        输入框打字
       │               │               │
       │        Coder自主择优     多轮对话调整
       │        说明理由          │
       │               │         轮次3：温和提示
       │               │         轮次5：矛盾检测+强引导
       │               │         轮次7：硬上限自动推进
       │               │         120秒超时：自动推进
       │               │               │
       ▼               ▼               ▼
  ┌──────────────────────────────────────────┐
  │  Coder 按选定方案写代码 + 自测            │
  │  → 进入辩论循环                           │
  └──────────────────────────────────────────┘
```

### 限制

| 规则 | 值 | 理由 |
|------|---|------|
| 每批方案数 | 2 个 | 对比清晰不过载（选择题 > 填空题）|
| 输入框对话上限 | 7 轮（3温和/5强引导/7硬上限） | 渐进式提示，不突然打断 |
| 超时 | 120 秒 | 自动交给 Coder 选最佳方案 |
| 方案生成模型 | Haiku | 控制 token 成本 |
| 矛盾检测 | Coder prompt 内置 | 发现用户反复时主动指出纠结点+给折中方案 |

### 为什么出 2 个不是 3 个

2 个方案形成明确对比（A vs B），帮用户理解 trade-off。
3 个方案第 3 个容易是前两个的折中，增加选择困难但不增加决策信息量。
输入框对话覆盖了 2 个不够的长尾场景。

### 不新增 Agent 的理由

Coder 自身已有方案设计能力。类比小团队：开发者自己设计方案 + lead（用户）审核。
「交给 Coder 选」时不需要 Attacker 参与——Attacker 在辩论阶段会审查代码，方案阶段重复参与增加 90 秒延迟不增加最终质量。

## 一-C、Strategy Diversification（策略多样化，新增）

### 问题：LLM 的局部最优陷阱

同一个 LLM 在同一个上下文中，重复问同一个问题，每次走同样的推理路径。
让 Coder 自己重试 3 次，和重试 1 次的成功率几乎一样——它跳不出自己的思维惯性。

### 解决：第 1 次失败就换角度（不等 3 次）

```
  Coder 第 1 次修复 → 自测失败
         │
         ▼  不是让它再用同样思路修第 2 次
         │
  Arbitrator 引导换角度：
  "你之前的修复失败了，原因是 XXX。
   请从以下不同角度考虑：
   A: 换数据结构/算法
   B: 换实现层级（函数→模块→路由）
   C: 换依赖/库
   D: 简化需求范围（只修核心部分）
   选择一个和第一次不同的角度。"
         │
         ▼
  用户审核替代方案
  [同意]  [不同意，我来说]
         │
         ▼
  Coder 按新角度修复 + 自测
         │
    通过了吗？
    │       │
   Yes      No → 再换一个角度 + 用户审核 → 第3次
    │              │
    │         第3次也失败 → 用当前最好版本 + Judge如实报告
```

### 触发时机对比

| 阶段 | 之前 | 现在 |
|------|------|------|
| 第1次失败 | Coder自己再试 | **立即**Arbitrator引导换角度+用户审核 |
| 第2次失败 | Coder自己再试 | 再换一个角度+用户审核 |
| 第3次失败 | 才找Arbitrator | 用当前最好版本+如实报告 |

## 二、辩论循环详细流程（Debate Loop，新增）

### 单轮辩论的 4 个 Stage

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
                    单轮辩论详细流程
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌──────────────────────────────────────────────────┐
  │  Stage 1: Coder 发言                              │
  │                                                  │
  │  第1轮: 根据需求+方案生成代码 + 自测               │
  │  第2轮+: 逐条回应上一轮攻击:                       │
  │    · 每条 finding 独立判断:                       │
  │      accept_and_fix (接受并修复)                  │
  │      rebut_with_evidence (用证据反驳)             │
  │    · 反驳必须有证据（run_code_snippet 执行结果）   │
  │    · 合并所有 accept 的修复到代码                  │
  │    · 自测通过后提交                               │
  └──────────────────┬───────────────────────────────┘
                     │
                     ▼
  ┌──────────────────────────────────────────────────┐
  │  Stage 2: 3 个 Attacker 并行攻击                  │
  │                                                  │
  │  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐│
  │  │  Security   │ │ Performance │ │ Correctness ││
  │  │  Attacker   │ │  Attacker   │ │  Attacker   ││
  │  └──────┬──────┘ └──────┬──────┘ └──────┬──────┘│
  │         │               │               │       │
  │         └───────────────┼───────────────┘       │
  │                         │                       │
  │    asyncio.gather: 同时发起，互不等待             │
  │    总耗时 = 最慢的那个（20-30秒）                 │
  │                                                  │
  │  第1轮: 从各自专业角度找问题                      │
  │  第2轮+:                                         │
  │    · 之前的问题修了吗？                           │
  │    · Coder 的反驳合理吗？                         │
  │    · 有新问题吗？                                │
  │    · 都OK了 → stance = "satisfied"               │
  └──────────────────┬───────────────────────────────┘
                     │
                     ▼
  ┌──────────────────────────────────────────────────┐
  │  Stage 3: 交叉审阅（Cross-Review）                │
  │                                                  │
  │  每个 Attacker 看到其他 Attacker 的发现           │
  │  · 补充对方遗漏的观点                             │
  │  · 支持或质疑对方的发现                           │
  │  · 没有补充就确认                                 │
  │  (≥2个 Attacker 成功时才触发)                     │
  └──────────────────┬───────────────────────────────┘
                     │
                     ▼
  ┌──────────────────────────────────────────────────┐
  │  Stage 4: 共识检测                                │
  │                                                  │
  │  检查所有 Attacker 的 stance:                     │
  │  · 全部 satisfied → 收敛，进 Judge                │
  │  · 有 attacking:                                 │
  │    · 还有轮次 → 回到 Stage 1（下一轮辩论）        │
  │    · 轮次用完 → 触发 Arbitrator 仲裁              │
  └──────────────────────────────────────────────────┘
```

### Coder 逐条回应的具体流程

```
  收到 3 个 Attacker 的攻击结果（每个可能有多条 finding）
         │
         ▼
  Step 1: 逐条审视
  ┌──────────────────────────────────────────┐
  │  Security #1: SQL 注入风险               │
  │  Security #2: 密码明文日志               │
  │  Performance #1: O(n²) 循环              │
  │  Correctness #1: 空值未处理              │
  │  Correctness #2: 边界溢出               │
  │  共 5 条 finding                         │
  └──────────────┬───────────────────────────┘
                 │
                 ▼
  Step 2: 逐条独立判断
  ┌──────────────────────────────────────────┐
  │  #1 SQL注入 → 说得对 → accept_and_fix    │
  │    → 改用参数化查询                       │
  │                                          │
  │  #2 密码日志 → 说得对 → accept_and_fix    │
  │    → 日志中 mask 掉密码                   │
  │                                          │
  │  #3 O(n²) → 不对 → rebut_with_evidence   │
  │    → 调 run_code_snippet 测性能           │
  │    → evidence: "1万条数据 0.003s"        │
  │                                          │
  │  #4 空值 → 说得对 → accept_and_fix        │
  │    → 加 None 检查                         │
  │                                          │
  │  #5 边界溢出 → 不对 → rebut_with_evidence │
  │    → evidence: "Python int 无溢出"       │
  └──────────────┬───────────────────────────┘
                 │
                 ▼
  Step 3: 统一修复 + 自测
  ┌──────────────────────────────────────────┐
  │  合并 3 条 accept_and_fix 的修复到代码    │
  │  run_code_snippet 自测 → 通过            │
  │  submit_response 提交                    │
  └──────────────────────────────────────────┘
```

### 多轮循环示例（3 轮）

```
Round 1:
  Coder: 生成初版代码 v1 + 自测
  Attacker×3 并行攻击: 发现 5 个问题 (0/3 satisfied)
  → 未收敛 → 继续

Round 2:
  Coder: 逐条回应 (3个accept修复 + 2个rebut反驳) → 提交 v2
  Attacker×3 再次审查:
    Security: "SQL注入已修! 但发现新问题: 缺少rate limiting" (attacking)
    Performance: "O(1)反驳成立。无新问题" (satisfied)
    Correctness: "空值已修! 无新问题" (satisfied)
  → 2/3 satisfied → 未收敛 → 继续

Round 3:
  Coder: rate limiting → rebut "不在需求范围内"
  Security: "不接受反驳" (attacking)
  Performance/Correctness: (satisfied)
  → 2/3 satisfied → 轮次用完 → 触发 Arbitrator 仲裁
```

## 五、用户操作 → 系统反应映射表

### Step 3：裁决报告页（两个按钮）

| 用户操作 | 系统反应 | 下一步 |
|----------|---------|--------|
| **接受全部裁决** | 直接采纳 Arbitrator 的 overall_verdict | → Step 5 合并裁决 |
| **我有异议** | 展开逐条详情界面 (Step 4b) | → 用户逐条选择 |
| **超时未操作** | 等同于"接受全部裁决" | → Step 5 |

### Step 4b：异议界面（逐条操作）

| 用户选择 | 系统处理 | 是否调 LLM | 对最终代码的影响 |
|----------|---------|-----------|----------------|
| **同意此裁决** | 保持原 verdict | 否 | 无 |
| **升级为必须修复** | verdict 改为 `must_fix` | 否 | Coder 多修一个问题 |
| **降级为驳回攻击** | verdict 改为 `dismissed`（安全红线项不可选） | 否 | Coder 少修一个问题 |
| **我有补充信息** | 用户输入文字 → 仅该条调 Arbitrator 重评 | 是（单条） | 取决于重评结果 |

### Step 5：三条终态路径

| 合并结果 | 判定条件 | 系统行为 |
|----------|---------|---------|
| **可交付** | must_fix=0 且 needs_human=0 | 当前代码直接进 Judge 出报告 |
| **修后交付** | must_fix ∈ [1, 3] 且无 critical | Coder 做最后一轮定向修复 → Judge |
| **需人工审查** | needs_human>0 或 must_fix>3 或有 critical 未修复 | 进 Judge 但标记 `requires_human_review=true` |

## 七、Arbitrator 裁决规则体系

### 四维评判矩阵

| 维度 | 权重 | 评判内容 |
|------|------|----------|
| **Severity Verification** | 30% | Arbitrator 独立重新评估严重度，不受 Attacker 自评影响 |
| **Evidence Quality** | 30% | 双方证据质量对比：有代码/测试 > 纯文字描述 |
| **Fix Feasibility** | 20% | 如果要修复，改动范围多大？风险多高？ |
| **Coder Rebuttal Validity** | 20% | Coder 的反驳是否有道理？ |

### 裁决原则（按优先级排序）

1. **安全问题零容忍**：涉及安全漏洞的争议，除非 Coder 给出了明确的代码级反驳证据，否则裁定攻击成立
2. **可复现性优先**：Attacker 提供了具体 test_input 且能触发问题 > 仅描述理论风险
3. **证据 > 推测**：双方都必须有代码级证据。纯理论推测不构成有效攻击，也不构成有效反驳
4. **修复成本纳入考量**：如果修复需要架构重构，但当前代码在绝大多数场景下工作正常，可以裁定为 deferred
5. **存疑从严**：安全类从严（must_fix），性能/风格类从宽（acknowledged）

### 安全红线（不可协商）

以下类别的 critical 级别 finding，用户**不允许降级或驳回**：

- SQL Injection
- Remote Code Execution (RCE)
- Command Injection
- Authentication Bypass
- Path Traversal
- Cross-Site Scripting (XSS)

## 八、关键设计约束

| 约束 | 值 | 理由 |
|------|---|------|
| HITL 最大轮次 | 1 轮确认 + 1 轮补充说明 | 防止无限循环 |
| 用户补充说明字数 | ≤ 500 字 | 控制 Arbitrator 重评估的 token 成本 |
| 超时时间 | 120 秒 | 动态适配，用户不在场时自动推进 |
| 用户可修改范围 | 升级/降级/补充说明 | 不可新增争议（那是新一轮辩论的事） |
| REST API 模式 | 跳过 HITL，自动接受裁决 | POST 接口不支持交互 |

```
└─────────────────────────────────────────────────────────────┘
```

**代码流转路径**：代码从始至终只有 Coder 能写和改。其他角色全部是评论者。

```
Round 1: Coder 生成 v1 ──→ current_code = v1
Round 2: Coder 修复 v2 ──→ current_code = v2
Round 3: Coder 修复 v3 ──→ current_code = v3
Final Fix: Coder 修复 v4 ──→ current_code = v4
Judge: 不碰代码，只写报告
返回给用户: current_code (最终版) + Judge 报告
```

## 十、Final Fix + Coder Self-Test + Arbitrator 复核（更新版）

### 核心变更

1. **取消独立 TestRunner 步骤** — Coder 自带自测能力，提交前必须自测通过
2. **取消激进版本回退** — 失败时换方案再试，不是放弃回退
3. **Docker 沙箱保留** — 作为 Coder `run_code_snippet` 工具的后端，对 Coder 透明

### Coder Self-Test 机制

```
Coder 每次提交代码前的内部流程（max_tool_turns=5）：

  Turn 1: 写/修改代码
  Turn 2: 调 run_code_snippet 执行代码 → 看能不能跑
  Turn 3: 构造测试用例（含 Attacker 的 test_input）→ 跑测试
          · 通过 → Turn 4: submit_response 提交
          · 失败 → 自己修 → Turn 4: 再测 → Turn 5: 提交

  结果：提交给系统的代码已经是 Coder 自测通过的
```

### 失败处理策略对比

| 之前（已废弃） | 现在 |
|---------------|------|
| TestRunner 外部验证失败 → 回退旧版本 | Coder 自测失败 → 自己修 → 还不行 → Arbitrator 给替代方案 |
| Arbitrator 发现未修复 → 标记 not_fixed | Arbitrator 发现未修复 → 给具体差距+替代方案 → Coder 补修 |
| 2次失败 → 强制回退到历史版本 | 替代方案也不行 → 用当前版本 + Judge 如实报告哪里没修好 |
| 唯一回退触发 | 只有 regression（修复把原来好的改坏了）才回退 |

### 关键规则

| 规则 | 值 | 理由 |
|------|---|------|
| Coder 自测轮次 | max_tool_turns=5 | 足够 test→fix→test→fix→submit |
| Arbitrator 替代方案 | 最多给 2 次 | 第1次换方案，第2次再换，还不行就用当前版本 |
| 回退条件 | 仅 regression | 修复把原来好的改坏了才回退，其他情况用当前版本 |
| Budget 不够时 | 跳过复核，直接进 Judge | 有结果比完美验证更重要 |

## 十一、requires_human_review 与 HITL 确认的区别

| 维度 | HITL 用户确认 (Step 3-4) | requires_human_review |
|------|--------------------------|----------------------|
| **位置** | 仲裁完成后、执行前 | 流程结束后、最终报告中 |
| **触发** | 每次仲裁都触发 | 仅在特定条件下 |
| **用户角色** | 审批者——看判决书决定是否同意 | 需要找专业工程师来 review |
| **解决的问题** | 用户对裁决有知情权和调整权 | 某些问题超出 AI 能力边界 |
| **触发条件** | — | needs_human 裁决、must_fix>3、critical 未修复 |

### Judge prompt 核心指令

```

- 用户看完报告应该知道：能不能用？不能用的话哪里需要动？怎么动？
```
