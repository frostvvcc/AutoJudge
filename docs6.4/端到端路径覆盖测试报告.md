# AutoJudge 端到端路径覆盖测试报告

**测试日期**: 2026-06-05  
**测试方法**: Path Coverage Testing（路径覆盖测试） + Scenario-based Testing（场景测试）  
**测试模型**: claude-haiku-4-5-20251001 (all agents)  
**测试后端**: anthropic_proxy (api.kunkunout.cn)  
**总测试时间**: 1244.8s（~20.7 min）  
**总 API 调用数**: 约 50 次  
**总测试用例**: 8 个场景，覆盖 5 条目标路径

---

## 1. 测试方法论

### 1.1 路径覆盖测试（Path Coverage Testing）

属于白盒测试的一种覆盖准则。基于程序的控制流图（此处为 LangGraph 状态图），枚举所有可能的执行路径，针对每条路径设计至少一个测试用例，确保每条路径至少被执行一次。

### 1.2 AutoJudge 状态图分支映射

```
plan ─→ coder ─→ [security, performance, correctness] (parallel)
                           │
                      cross_review
                           │
                   check_consensus_edge
                    ╱       │       ╲
            "converged" "continue" "budget_exceeded"
                │           │           │
              judge       coder     arbitration
                │           │       ╱        ╲
               END        (loop)  "deliver"  "fix"
                                    │          │
                                  judge    final_fix
                                    │          │
                                   END       judge
                                               │
                                              END
```

### 1.3 目标路径清单

| 路径 ID | 分支判定序列 | 触发条件 |
|---------|-------------|---------|
| **A** | consensus → converged (≤1 round) | 所有 Attacker stance=satisfied |
| **B** | consensus → continue → converged (2+ rounds) | 首轮有 attacking，后续变 satisfied |
| **C** | consensus → budget_exceeded → arb → deliver | 未收敛 + 超轮次/预算 → 仲裁判可交付 |
| **D** | consensus → budget_exceeded → arb → fix → final_fix | 仲裁判 must_fix → 修复 |
| **E** | budget_exceeded → arb(no disputes) → judge | 仲裁入口但无实质争议 |

## 4. 发现的 Bug

### BUG-1: Coder Tool Turn 耗尽导致代码丢失 [严重度: Critical]

**现象**: 7/8 场景 code_length=0，只有 T1（最简单的任务）成功产出代码。

**根因**: 
Coder 的 tool_use 循环最多允许 6 轮 API 调用（`max_tool_turns=5` → `range(6)`）。对于复杂任务，Coder 把全部 5 个 tool turn 用在 `run_code_snippet` 自测上，耗尽后循环退出，**从未调用 `submit_response`**。最终 response 是最后一次 `run_code_snippet` 的结果，不包含 `updated_code` 字段。

**证据**: 
- T6 (递归下降): coder 用了 6 次 API 调用 (12019 tokens, 129s)，`code=0`
- T7 (LRU Cache): coder 用了 6 次 API 调用 (14844 tokens, 163s)，`code=0`
- T1 (两数之和): coder 只用 1 次 API 调用 (直接 submit_response)，`code=177 chars`

**影响**: 
- 攻击者审查时没有代码可看 → stance 数据不可靠
- Judge 评估空代码 → star=1, confidence=0, 所有分数=0
- 整个辩论流程在 Coder 节点就已失效

**位置**: `app/llm/client.py` → `_call_anthropic_proxy()` 第 398-448 行

**修复建议**: 
在循环结束后增加代码回退提取逻辑：如果 `code is None`，从 `conv_messages` 中找最后一次 `run_code_snippet` 的 `input.code` 作为 fallback。或者在最后一轮强制切换 `tool_choice` 为 `submit_response`。

---

### BUG-2: Attacking Stance 但 Findings 为空 [严重度: High]

**现象**: T7 中 correctness 和 security 均为 `stance=attacking`，但 `findings_count=0`。

**根因**: 
`_extract_unresolved_disputes()` 要求 `structured.findings` 非空才提取争议：
```python
for finding in structured.get("findings", []):
    disputes.append({...})
```
当 Haiku 输出 `stance="attacking"` 但 `findings=[]` 时，循环体不执行，0 条争议被提取。仲裁节点返回 "无实质未解决争议，等效收敛"。

**影响**: 
- 系统认为代码没问题（等效共识），但实际有 2/3 的攻击者不满意
- 仲裁路径被短路，永远无法触发 must_fix

**位置**: `app/engine/graph.py` → `_extract_unresolved_disputes()` 第 503-525 行

**修复建议**: 
当 `stance=attacking` 但 `findings` 为空时，生成一条合成争议：
```python
if structured.get("stance") == "attacking" and not structured.get("findings"):
    disputes.append({
        "attacker": msg["agent"],
        "finding": structured.get("message", "Attacker 有未解决的顾虑但未提供具体 findings"),
        "severity": "medium",
        "coder_response": "未回应",
    })
```

### BUG-3: 共识误判 — 少数即代表全体 [严重度: Medium]

**现象**: 当 3 个 Attacker 中只有 1 个返回了结构化 stance 数据时，共识检测只基于这 1 个 Attacker 的判断。

**根因**: 
`ConsensusDetector.check_consensus()` 只统计有 `stance` 字段的 Attacker：
```python
if msg.structured and "stance" in msg.structured:
    attacker_status[msg.agent] = (msg.structured["stance"] == "satisfied")
if not attacker_status:
    return {"converged": False}
all_clear = all(attacker_status.values())
```
如果 2 个 Attacker 的 API 调用失败（返回空 structured），`attacker_status` 只包含 1 个 entry，`all({True}) = True` → converged。

**位置**: `app/engine/consensus.py` 第 12-29 行

**修复建议**: 
共识检测应感知活跃攻击者列表。如果有活跃攻击者缺失 stance 数据，视为未收敛。

---

### BUG-4: Haiku 模型作为攻击者过于温和 [严重度: Medium / Design Issue]

**现象**: 
在 8 个测试场景中：
- 6 个场景所有攻击者 stance=satisfied（包括 SQL 注入任务 T8）
- 1 个场景有 2 个攻击者 stance=attacking 但 findings=0（T7）
- 只有 T1 产出了有效结果（因为代码确实简单正确）

**根因**: 
claude-haiku-4-5 作为轻量模型，在受限 token 预算下（max_tokens=2000 per attacker），倾向于生成最简回复。配合 `tool_choice: forced submit_review`，Haiku 生成了格式正确但内容空洞的结构化输出（stance=satisfied, findings=[]）。

**影响**: 
- 辩论机制失效：攻击者从不真正审查代码
- 多轮辩论路径（Path B）永远不会被触发
- 仲裁路径（Path C/D）需要依赖非共识，但共识总是达成

**建议**: 
- 攻击者使用更强的模型（至少 Sonnet），或增加 per-attacker token budget
- 在 model_router 中将攻击者从 Haiku 升级为 DEFAULT_MODEL
- 或添加 "minimum review depth" 校验：如果攻击者的输出 token 数低于阈值（如 200），视为无效审查并重试

---

### BUG-5: Judge 在无代码时仍产出评分 [严重度: Low]

**现象**: 当 code_length=0 时，Judge 仍然运行并产出 star_rating=1, confidence=0, 所有 score=0。

**影响**: 前端展示了无意义的评分结果。

**建议**: 
在 `judge_node()` 入口检查 `state.current_code` 是否非空。如果为空，返回标记性 report。

---

### BUG-6: Budget 统计不含缓存 Token [严重度: Low]

**现象**: 
`budget_spent` 仅统计 `input_tokens + output_tokens`，不含 `cache_read_input_tokens`。攻击者显示 142 tokens（实际 prompt 含 ~2000 tokens 的 system prompt，被缓存后不计入）。

**影响**: 
`check_consensus_edge` 中的 `budget_spent >= budget_total * 0.85` 判定基本不会触发（实际消耗远高于统计值）。

## 7. 根因分析与修复优先级

### 阻塞链分析

```
BUG-1 (代码丢失)
    ↓ 导致
BUG-4 (攻击者无代码可审 → stance 不可靠)
    ↓ 导致
BUG-2 (attacking 但无 findings)
    ↓ 导致
路径 B/C/D 永远不可达
    ↓ 导致
路径覆盖率仅 40%
```

### 修复优先级

| 优先级 | Bug | 影响范围 | 修复难度 |
|--------|-----|---------|---------|
| **P0** | BUG-1: 代码提取失败 | 7/8 场景失效 | 低（~20 行代码） |
| **P1** | BUG-2: 空 findings 争议丢失 | 仲裁路径完全失效 | 低（~10 行代码） |
| **P1** | BUG-4: 攻击者模型选择 | 辩论机制失效 | 配置更改 |
| **P2** | BUG-3: 共识误判 | 鲁棒性 | 低（~5 行代码） |
| **P3** | BUG-5: 无代码 Judge 空跑 | 用户体验 | 低 |
| **P3** | BUG-6: Budget 统计遗漏 | 预算控制失效 | 低 |

## 8. 结论

### 已验证的路径
1. **Path A (快速共识)**: 全流程正常，T1 实现了完整的 plan → code → review → judge
2. **Path E (仲裁空分派)**: 仲裁节点可达，但因 BUG-2 被短路

### 未能验证的路径
3. **Path B (多轮辩论)**: 被 BUG-1 + BUG-4 阻塞
4. **Path C (仲裁→交付)**: 被 BUG-2 阻塞
5. **Path D (仲裁→修复)**: 被 BUG-2 + BUG-1 阻塞

### 未测试的功能
- HITL interrupt（需要 WebSocket 模式）
- 安全红线校验（需要仲裁裁决 critical security）
- 策略多样化（需要 final_fix 节点触发）
- 三层记忆（需要 ChromaDB + Redis 预填数据）
- 4 级降级（需要系统级故障注入）

### 建议下一步
1. 修复 BUG-1（P0），然后重跑全部 8 个场景
2. 修复 BUG-2（P1），验证仲裁路径 C/D
3. 将攻击者模型切换为更强模型后重测，验证路径 B
4. 添加 WebSocket 集成测试，覆盖 HITL interrupt 路径
